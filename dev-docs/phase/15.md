# 15 - realtime latency

Map moves and forced joins reach other users too slowly.

## 1. Faster forced joins

When A walks into B, B's screen only switches to the meeting after `proximity::gather` has finished. `gather` is slow for two reasons:

- It sets up the movers one after another (`move_into` in a `for` loop). Each one creates a Chime attendee and runs several DB queries.
- Every `move_into` calls `broadcast_list`, so the whole org gets the meeting list pushed once per person moved.

Change:

- Set up the movers in parallel. The first mover must still finish alone first, because it claims the room. The caller still goes last.
- Push the meeting list once, at the end of `gather`, not once per mover.

## 2. Map moves over AppSync Events

Take the Lambda off the map's hot path. Clients publish their moves directly to an AppSync Events API, and every map viewer in the org receives them through a subscription. The backend keeps persistence and authorization.

## Channels

One channel per user per org: `/map/{org_id}/{user_id}`.

- A user publishes only to their own channel.
- A map viewer subscribes to `/map/{org_id}/*`.
- The event payload is `{"x", "y"}`; the sender is identified by the channel path.

## Auth

- **Map token:** `GET /map/org/{org_id}/realtime` checks `require_member`, then returns `{endpoint, token}`. The token is a short-lived JWT (15 min) signed with `JWT_KEY` and carrying `sub` and `org_id`.
- **Authorizer:** a new `map-authorizer` binary in the backend crate, deployed as its own Lambda. It verifies the token's signature and expiry, with no DB access, then checks the channel:
  - publish: `/map/{org_id}/{sub}` only
  - subscribe: `/map/{org_id}/*`
- Authorizer results are cached per token (`ttlOverride` = the token's remaining lifetime), so a publish only pays the authorizer's cost once.
- The frontend refreshes the map token before it expires and reconnects with the new one.

## Backend

- Add the `realtime` route and a `map_token` issue/verify pair next to `auth::issue`/`verify`.
- `move_route` only persists (phase 14's `persist` flag). It broadcasts through the messenger (`MOVE_CHANNEL`) only when AppSync isn't configured (`MAP_EVENTS_ENDPOINT` unset), which is the local fallback.
- `ACTIVE_CHANNEL`/`map_active` stay as they are, for `positions_route`.

## Frontend

- `lib/mapEvents.js`: connects to the AppSync Events WebSocket, subscribes to `/map/{org_id}/*`, and publishes over the same socket.
- `useMapSession`: publishes every move to AppSync, and sends `moveInMap` only for persisted moves. When `realtime` returns no endpoint, it keeps the current messenger path.

## Infra

- `infra/map_events.tf`: `aws_appsync_api` (Event API) with a Lambda authorizer, plus an `aws_appsync_channel_namespace` named `map`.
- The authorizer Lambda gets `JWT_KEY` from the same source as the API Lambda.
- The API Lambda gets `MAP_EVENTS_ENDPOINT`. Add it to the `backend_env_file` output.

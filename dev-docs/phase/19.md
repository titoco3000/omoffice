# 19 - shared board

Draw on top of a shared screen. Any attendee can draw; strokes are freehand
paths, not raw point spam; an eraser tool removes a whole stroke by clicking
on it. Ephemeral, same as `meeting_chat` -- no DB table -- but unlike chat, a
client that joins mid-share pulls the current strokes from the share's owner
(see request/response below). Nothing is stored anywhere longer than the
share itself: when the share ends (owner stops sharing or disconnects), the
content tile disappears for everyone the same way it does today, the board
overlay mounted on it unmounts with it, and the drawing is gone on every
client -- no separate "clear" message needed, this falls out of strokes
living only in that component's state.

## Backend

New `backend/lib/features/meetings/board.rs`, modeled directly on `chat.rs`:

- `CHANNEL = "meeting_board"`.
- `register(messenger, db)` handles two message shapes on the one channel:
  - `{ "type": "add", "meeting_id", "stroke": { "id", "color", "width", "points": [[x,y], ...] } }`
  - `{ "type": "erase", "meeting_id", "stroke_id" }`
- Same trust rule as chat: look up `super::attendee_ids(&db, meeting_id)`,
  drop silently if `from` isn't one of them. Broadcast to the others
  (`from` doesn't need its own echo -- it already drew locally).
- No persistence, no new table. A late joiner's client requests the drawing
  so far from that specific tile's owner -- add two more message shapes,
  both *targeted* sends (one recipient, not "others" -- precedent:
  `FORCE_CHANNEL` in `mod.rs:534`, `messenger.send(CHANNEL, &[target], ...)`):
  - `{ "type": "request_state", "meeting_id", "owner_id" }` -- backend
    checks `from` and `owner_id` are both current attendees, forwards to
    `owner_id` only as `{ "type": "request_state", "meeting_id", "for": from }`.
  - `{ "type": "state", "meeting_id", "to", "strokes": [...] }` -- owner's
    client sends this in response; backend checks `to` is an attendee,
    forwards to `to` only. No check that `from` is actually the tile's
    owner beyond attendee membership -- same trust bar as `chat.rs` (a
    meeting has no roles to gate this by, only "are you in it"), and the
    worst case is a wrong/empty board for one drawing feature, not
    something worth a stricter check.
  - Because a meeting can have two simultaneous shares, `owner_id`/tile
    identity must travel in these messages -- never assume a single owner
    per meeting.
- Wire `board::register(&messenger, db.clone())` into `main.rs` next to the
  existing `chat::register` call.

## Frontend

New `frontend/src/features/meetings/panel/BoardCanvas.jsx`:

- One `<canvas>` absolutely positioned over a content-share tile only
  (`tile.isContent` in `MeetingPanel.jsx`), sized to the tile's container
  via `ResizeObserver`.
- **Coordinate mapping (do this, not naive 0-1 on the container):** the
  `<video>` is `object-fit: cover` per `MeetingTile.jsx` today, but a
  screen-share tile should switch to `object-fit: contain` -- cropping
  someone's shared screen to draw on is worse than letterboxing it. Compute
  the actual rendered video rect inside the container from
  `videoEl.videoWidth/videoHeight` vs container aspect ratio (letterbox
  top/bottom or left/right), normalize stroke points to *that* rect, not
  the container. Recompute on `loadedmetadata` and on resize. Every viewer
  redoes this math locally off their own tile size, so normalized points
  stay correct across different window sizes without the sender knowing
  anyone else's layout.
- **Drawing:** pointerdown starts a local point buffer + draws live to the
  canvas immediately (no round trip for your own strokes). pointerup
  finalizes it into a stroke object (`{id: uuid(), color, width, points}`,
  points normalized per above) and sends one `type: "add"` frame via
  `messenger.send(CHANNEL, {...})`. Simplify the point buffer before
  sending (drop points closer than ~2px, or run a basic Douglas-Peucker)
  so a long stroke isn't hundreds of points.
- **Eraser:** separate tool mode. pointerdown/move while erasing hit-tests
  the cursor against every stroke's segments (point-to-segment distance,
  threshold scaled to canvas size, ~6-8px at 1x). First hit: remove locally
  by id, send `type: "erase"`.
- **State:** `Map<strokeId, stroke>` per content-tile id, plain component
  state. `messenger.on(CHANNEL, handler)` in a `useEffect`, applies
  `add`/`erase` from peers the same way local actions do. Redraw the whole
  canvas from the map on any change -- simplest thing, fine at this scale.
- **Catch-up on join:** on mount, if this client isn't the tile's owner
  (`chime.externalToUserId(tile.externalUserId) !== myId`), send
  `{ type: "request_state", meeting_id, owner_id }` once. The owner's own
  `BoardCanvas` instance handles `request_state` in its message handler by
  replying `{ type: "state", meeting_id, to: for, strokes: [...current map values] }`.
  Requester applies the reply by replacing its whole map (last write wins;
  if a stroke was mid-flight from someone else at the same moment, it
  arrives separately as its own `add` right after -- fine, not worth
  sequencing against).
- **Toolbar:** pen/eraser toggle + maybe a color swatch, shown only when
  hovering/focused on a content tile (reuse the existing hover-controls
  overlay pattern in `MeetingTile.jsx`), or a persistent small strip along
  the tile edge if hover-only proves hard to discover.

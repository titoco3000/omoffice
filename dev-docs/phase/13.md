# 13 - office map

## Preparation

Add a "graphics mode" setting to /profile, with the options "map" or "no-graphics".
If on mode "map", the contents of /in should be replaced by a canvas filling the available space and the OrgOnlineView should be rendered on the sidebar in desktop, and via a toggle on the botton right on mobile.

## implementation

On this canvas, lets implement a map system. 

How it works:

Every user gets an X and Y coordinate and a map_active in their org participation.
In the frontend, a grid of size OFFICE_SIZE x OFFICE_SIZE (lets say 100 for now) is rendered using a canvas, and each user that is online appears on their cell as an avatar.

If multiple users are on the same cell, they are each rendered with a small offset from the center of the cell.

Users are allowed to move to different cells by either navigating with the arrow keys or clicking on a cell.
There is a fixed time that users are allowed to change their cells: 1 / USER_SPEED. If the user holds an arrow key, it moves them by one cell and starts a timer to allow moving again. On timer end, if the arrow is still clicked, it repeats the process. Mouse clicks during the cooldown are stored and only apply after the cooldown. Multiple clicks during the cooldown override each other, with only the last one beeing applied.

When a user changes cell the event is sent to all online users that have map_active set to true. Their avatar is translated at a fixed speed to the target cell.

The user position is bound from 0 to OFFICE_SIZE - 1

# 13.1 - optimization

## planning

This program has a 'map' feature, where one user moves and it reflects on the other's screen. But there is too much delay - the lambda needs to do multiple accesses to the DB before propagating the info forward. One optimization we can make is caching authentication tokens in the lambda instance, but what else?

## implementation

A map move is slow to reach other users: `move_route` runs ~5 queries plus one connection lookup per recipient and one push per connection, all in sequence. Implement the following optimizations:

## 1. Fewer queries

- **Messenger:** add `connections::for_users(user_ids)` (`WHERE user_id = ANY($1)`) and use it in `Messenger::send`, so all recipients' connections come from one query.
- **Rbac:** add `online_member_ids(org_id)` (`SELECT user_id FROM org_users WHERE org_id = $1 AND online`).
- **Map:** `move_audience` uses `online_member_ids` and runs it concurrently with the `map_active` query.

## 2. Parallel pushes

`Messenger::send` delivers to all connections concurrently (`for_each_concurrent`, limit 16).

## 3. Write and broadcast concurrently

`move_route` clamps the position, then runs `set_position` and the broadcast together with `tokio::join!`.

## 4. Persist less often

`MoveBody` gets a `persist` flag. Every move is broadcast, but only moves with `persist: true` are written. The frontend sets it when movement stops, at most once per second while moving, and on canvas unmount.

# 6 - Database

### Prompt

Lets add a SQL database to this project.

Use Aurora DSQL. It is serverless, scales to zero, has a public endpoint (so the
lambda stays out of a VPC and we avoid a NAT gateway) and authenticates with IAM
tokens instead of a password, so there is no secret to rotate. Terraform owns the
cluster, one per stage, named the same way as everything else.

**No local database**

There is no local DSQL - no emulator, no container image. Instead, local runs talk to the real `dev` cluster, the same way `make run dev`
already sources `backend/.env.dev` and reads the real per-stage JWT secret from
Secrets Manager with my AWS profile. The database is that same pattern - no new
machinery, no compose file, no seed script.

**Schema and migrations**

- Migrations live in the repo as ordered, checked-in SQL files.
- Each migration has both an up and a down. Down migrations can lose data
  (dropping a column drops what was in it) - that is expected, but the target
  should say so before it runs.
- Applying and reverting are make targets, and both can run against dev or prod.
- I want to see which migrations have and have not been applied to a given
  database without guessing.

The tool tracks applied migrations in a ledger table in the database. Normally it
writes that ledger row inside the same transaction as the schema change, so a
crash rolls back both and the ledger can never disagree with the database. DSQL
does not allow DDL and DML in one transaction, so that guarantee is not
available and the ledger has to be written separately.

Ordering alone does not fix it - write the ledger first and a crash leaves the
ledger claiming a migration that never ran, which fails silently much later.
Use three steps and two states instead:

1. insert the ledger row as `pending`
2. run the DDL
3. update the row to `applied`

A crash anywhere leaves a `pending` row, so the next run can stop with a named
error telling me which migration was interrupted, instead of lying in either
direction. Reverting works the same way in the other direction.

Check the tool you pick actually behaves this way against DSQL rather than
assuming it does - most assume postgres transaction semantics. `sqlx`'s migration
table already carries a `success` flag which is the same idea, but verify it is
set correctly when transactions are not available. If off-the-shelf tools fight
DSQL here, a hand-rolled runner is about a hundred lines and gives exactly these
semantics; that is an acceptable outcome, not a failure.

**CLI access**

- One make target that opens a SQL shell against dev or prod.
- It generates a fresh IAM auth token each time. I should never look up an
  endpoint or a password by hand.

**Write DSQL, not postgres**

DSQL supports a subset of postgres. At least the following, though this list
moves - foreign keys were unsupported until August 2026 and now work, so check
the current compatibility docs before designing the schema:

- no sequences, so no `SERIAL`/`BIGSERIAL` - use UUID primary keys
- no views, no triggers, no extensions
- indexes are created with `CREATE INDEX ASYNC`, which returns immediately and
  builds in the background
- DDL and DML cannot share a transaction, and there are limits on multiple DDL
  statements in one transaction
- optimistic concurrency - a write can fail at commit with a conflict, so writes
  need a retry path
- 10,000 row limit per transaction

Don't add indexes yet. There is no data to speak of, so they buy nothing, and
skipping them keeps the first migrations simple.

**Schema to start with**

Just enough to prove it works end to end:

- a `users` table keyed by the email that already comes out of
  `/auth/request-key/{email}`
- a `meetings` table recording meetings created through `POST /private/meetings`
  (code, creator, created_at)

Add a private route that lists my past meetings, and something in the frontend to
show it, so there is a visible thing to click.

**Fit with what already exists**

- `sqlx` with the postgres + rustls features. The default `aws-lc-rs` backend
  needs cmake and a C toolchain the zig cross-build does not have.
- Use the compile-time query macros (`sqlx::query!`) and commit the `.sqlx/`
  offline cache, since `make build` cross-compiles with no database to reach.
  Add `cargo sqlx prepare --check` to `make lint` so a stale cache fails the lint
  instead of surfacing at deploy time, and a `make db-prepare` (or similar) to
  regenerate it.
- Connection config goes through the same `.env.<stage>` handoff as everything
  else: `infra/make output <stage>` prints whatever the backend needs, and
  `backend/make deploy` fails with a pointer to that command when it is missing.
- IAM auth tokens expire, so the connection pool has to be able to fetch a fresh
  one rather than holding the one it got at cold start.
